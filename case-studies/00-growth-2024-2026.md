# What changed between 2024 and 2026

A methodology is only interesting if you can see what it corrects. This is the
before.

| | Prose generation tool | AI CV product | Rules engine + client |
|---|---|---|---|
| **Period** | Jun – Nov 2024 | Feb – Jun 2026 | Jun – Aug 2026 |
| **Stack** | Laravel / PHP | FastAPI + React | Python 3.12 + TypeScript |
| **Commits** | 11 | 183 | 2,294 |
| **Test files** | 3 | 27 | 276 |
| **Decision records** | none | none | 39 |
| **Tracked tickets** | none | 32, as branch names | 292 closed, as files |
| **CI** | none | yes | yes, plus strict typing |
| **Agent policy** | none | contributing guide | enforced, with checklist |

---

## 2024 — the prose tool

Five months, eleven commits. It generated long-form fiction through a
provider abstraction covering five model backends, including a local one, with
rolling summarisation to hold context across chapters.

The architecture instinct was sound. Designing for provider independence in
mid-2024, before that was standard advice, is the part I would still defend.

Everything around it was not.

- The README was the framework's stock boilerplate, never replaced.
- Commit messages included *"no idea, getting better though"* and *"Not sure"*.
- Three test files.
- No tickets, no decision records, no definition of done.
- A development TLS key was committed to the repository.
- Five JVM crash dumps were committed, disclosing the host's full `PATH`:
  username, VPN and SSH clients, virtualisation software, and exact versions
  of the web server, database and language runtime.

The key was a local development certificate, identical on every install of
that toolchain, and the repository was never public. The exposure was
therefore close to nil. That is not the point. The point is that nothing in
how I worked would have caught it if it had mattered, and I did not know it
was there until I went looking two years later.

## 2026 — the CV product

Four months, 183 commits, 27 test files, CI, a pull-request template, database
migrations. Work tracked as numbered tickets, though only as branch names —
the ticket text lived in a chat window and is gone.

Secrets handling was correct by then: no credentials committed, no secrets in
history, a checked-in example environment file and nothing else.

What was still missing was any record of *why*. Reconstructing a decision from
this project means reading diffs and guessing.

## 2026 — the rules engine and its client

Two months, 2,294 commits, 292 closed tickets, 39 decision records, 276 test
files, and a written policy governing AI contributors that was enforced rather
than aspirational.

The jump in throughput is not the interesting number. Most of that code was
written by AI agents, and raw agent output is cheap. What made it usable was
the constraint system around it: a ticket as a binding contract, an escalation
path that made "I do not have enough information" a success state, tiered
review with separation of duties, and machine-checked gates no contributor
could argue past.

That project's agent policy also included, from early on:

> Do not commit secrets, credentials, or the rules PDF.

The 2024 project is why that line exists.

---

## The through-line

The change across two years is not that I learned new tools. It is that the
work acquired **controls**: written rules, enforced gates, recorded decisions,
separated duties, and an audit trail that survives the people and the sessions
that produced it.

The most useful single act in assembling this repository was auditing my own
old work and finding something I would rather not have found. That is also the
reason the 2024 column is in the table at all.
